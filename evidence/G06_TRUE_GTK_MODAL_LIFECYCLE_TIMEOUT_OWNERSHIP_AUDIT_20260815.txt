======================================================================
AUDIT A — PRODUCT MODALITY IS SYNCHRONOUS BY DESIGN
======================================================================

ASSUMPTION UNDER TEST
An automated GTK gate may invoke an operation that can open a modal dialog and rely on a
large outer process timeout to recover if the dialog appears.

CONTRADICTORY / STRESSING EVIDENCE
- Mousepad's save-changes path constructs a GtkMessageDialog and calls gtk_dialog_run();
  the product waits synchronously for a response and only then dispatches SAVE, SAVE AS,
  DON'T SAVE or CANCEL.
- Leafpad and L3afpad both test the buffer modified flag before destructive lifecycle
  transitions, then synchronously call their question-dialog runner; their dialog runner
  itself calls gtk_dialog_run() and returns only after a user response.
- Graphium's published GtkLifecycleUI follows the same mature GTK model: its unsaved
  changes dialog is modal and synchronous by design.

ALTERNATIVE MATURE MODEL
Treat nested modal execution as a legitimate product state, not as a test anomaly. A test
must either:
1. prove the scenario cannot reach a modal boundary; or
2. own a deterministic response before invoking the modal-capable action.

GRAPHIUM CONSEQUENCE
A G06 View test that does not intend to test lifecycle dialogs must never cross
Saved -> Modified -> Open/New/Quit. Clean state is a precondition, not an afterthought.

DECISION
ADOPT: explicit clean lifecycle boundaries before every fixture replacement.
REJECT: outer timeout as the primary mechanism for escaping a modal product state.

======================================================================
AUDIT B — RESPONSE OWNERSHIP MUST PRECEDE THE TRIGGER
======================================================================

ASSUMPTION UNDER TEST
If a dialog appears unexpectedly, the test can notice it after the product call returns.

CONTRADICTORY / STRESSING EVIDENCE
Mousepad's test plugin explicitly distinguishes actions that open blocking dialogs. For
blocking actions it schedules a GLib timeout BEFORE action execution. The callback scans
visible top-levels for GtkDialog and calls gtk_dialog_response(). The callback therefore
runs inside the nested dialog loop and can release the product call. Mousepad also removes
pending GLib sources when monitoring ends.

Published Graphium G04/G05 already use the same principle:
- G04 schedules a callback before operations expected to show a warning dialog.
- G05 schedules callbacks before renderer-warning and Go-to-Line dialog paths.

ALTERNATIVE MATURE MODEL
Expected modal:
  arm deterministic responder -> invoke product action -> verify expected result -> remove
  any still-pending source.

Unexpected modal in a scenario declared non-modal:
  arm a tripwire -> invoke product action -> if a dialog appears, record its identity and
  respond only to unwind the nested loop -> FAIL the scenario immediately after return.

GRAPHIUM CONSEQUENCE
The G06 View semantic gate has EXPECTED_MODAL_COUNT=0. It must not silently cancel and
continue. An unexpected dialog is a gate failure, but the harness must own enough recovery
to report it without waiting for the process watchdog.

DECISION
ADOPT: schedule-before-trigger response ownership.
ADOPT: unexpected-modal tripwire that unwinds then FAILS.
REJECT: generic auto-cancel that permits the scenario to continue as PASS.

======================================================================
AUDIT C — LIFECYCLE STATE OWNERSHIP IS STRONGER THAN VISUAL STATE
======================================================================

ASSUMPTION UNDER TEST
A title/status showing Saved is sufficient proof that a test may replace the active file.

CONTRADICTORY / STRESSING EVIDENCE
Graphium's published contract defines Saved/Modified by state identity. G04/G05 regression
gates already return scenarios to an exact clean state before changing fixtures. G05's
`establish(..., clean=True)` creates a new exact Saved state for independent Search cases.

ALTERNATIVE MATURE MODEL
Fixture replacement precondition:
  session.modified == False
  AND history.current_state_id == session.saved_editor_state_id
  AND no response-owned modal remains active.

GRAPHIUM CONSEQUENCE
`open_clean()` and performance-fixture opens must assert exact Saved identity both before
and after Open. The G06 Compact Status mutation test must restore with real Graphium Undo,
then prove exact clean state before the next fixture.

DECISION
ADOPT: exact state-ID boundary as the gate oracle.
REJECT: title/status text as the sole lifecycle oracle.

======================================================================
AUDIT D — TIMEOUT OWNERSHIP
======================================================================

ASSUMPTION UNDER TEST
One large shell `timeout` around an integrated gate is sufficient timeout ownership.

CONTRADICTORY / STRESSING EVIDENCE
- Mousepad uses action-local GLib sources for blocking-dialog monitoring and explicitly
  removes pending sources when the monitoring lifecycle ends.
- Graphium G04 FIRST_EDITABLE owns a local deadline, diagnoses missing/partial handshake,
  then terminates and escalates to kill if necessary.
- Graphium comparator tooling similarly owns process deadlines and cleanup.
- R2 showed that a 90-second outer timeout did contain the hang, but it identified only the
  whole G06 gate rather than the accidental lifecycle boundary that caused it.

ALTERNATIVE MATURE MODEL
Two layers with separate purposes:
1. INTERNAL OWNERSHIP: scenario-specific state checks, expected responders and unexpected
   dialog tripwires; every GLib source ID is owned and removed/cancelled during cleanup.
2. OUTER WATCHDOG: process-level containment only. It is a last-resort crash/hang guard,
   not a normal dialog oracle and never a substitute for lifecycle ownership.

Each gate emits BEGIN/PASS phase markers around modal-capable or long-running boundaries.

GRAPHIUM CONSEQUENCE
A future candidate runner may still use bounded subprocesses, but a hit on that bound is a
harness/product investigation trigger; normal modal paths must be diagnosed earlier by the
gate itself.

DECISION
ADOPT: internal ownership + outer containment.
REJECT: one monolithic timeout as semantic authority.

AUDIT E — NEW G06 QUALIFICATION TOPOLOGY
======================================================================

ASSUMPTION UNDER TEST
After repairing R2, the correct next move is an R3 of the same integrated NON-CANDIDATE
checkpoint.

CONTRADICTORY / STRESSING EVIDENCE
The line has already consumed its two allowed operational failures. Reissuing the same
integrated checkpoint would preserve the wrong qualification topology and encourage
trial-and-error.

ALTERNATIVE MATURE MODEL
No more G06 pre-candidate integrated checkpoint. The next T480 product qualification, only
when separately authorized, is a candidate runner that orchestrates independent fresh-
process gates:

LANE 1  G04 True-GTK regression — published lifecycle/editor oracle.
LANE 2  G05 True-GTK Search regression — published search oracle.
LANE 3  G06 True-GTK View semantics/content-neutrality — EXPECTED_MODAL_COUNT=0,
        clean lifecycle boundaries, unexpected-modal tripwire.
LANE 4  G06 View performance/Lightweight Budget — clean fixture opens only.
LANE 5  one-process/one-window/one-document topology + shortcut collision audit.
LANE 6  exact Graphium FIRST_EDITABLE regression.
LANE 7  common FIRST_VISIBLE Leafpad/L3afpad/Mousepad/FeatherPad comparator.
LANE 8  G05 Search performance regression.
LANE 9  G06 startup self-regression gate against certified G04 baseline.
LANE 10 final human G06 View validation only after lanes 1-9 PASS.

Each lane is a fresh process or already-isolated external benchmark. A lane failure stops
qualification; no later lane runs. No lane inherits a Modified editor state from another.

GRAPHIUM CONSEQUENCE
The retired checkpoint is evidence only. It is not a template to patch and rerun.

DECISION
REJECT: G06 integrated NON-CANDIDATE checkpoint R3.
ADOPT: fresh-process gate matrix for the eventual G06 desktop candidate.
